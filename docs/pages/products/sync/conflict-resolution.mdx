Conflict resolution defines what happens when multiple clients edit the same
document before they have received each other’s changes. Sync resolves these
edits through the structure of your Storage document, so clients converge on the
same result without application-level merge code.

## Why conflicts happen [#why-conflicts-happen]

Network messages take time. Two users can drag different shapes, rename the same
field, reorder a list, or insert text at the same moment. A request/response API
often handles this by replacing an entire document, which can discard one
person’s work.

Sync sends operations against conflict-free data types instead. Unrelated
operations can be preserved and combined.

## How data types combine edits [#how-data-types-combine-edits]

### Objects [#objects]

Properties in a [`LiveObject`](/docs/api-reference/liveblocks-client#LiveObject)
are edited independently. If one client changes `x` while another changes
`color`, both updates remain.

```ts
const shape = storage.get("shapes").get("shape-1");

shape.update({ x: 120 });
// Another client can update `color` at the same time.
```

When clients replace the same atomic property concurrently, Sync selects one
value consistently across every client. Split independently edited values into
separate properties when both updates need to survive.

### Maps [#maps]

Each key in a [`LiveMap`](/docs/api-reference/liveblocks-client#LiveMap) is
independent. This makes maps a good default for collections of entities with
stable IDs.

```ts
const shapes = storage.get("shapes");

shapes.get("shape-1")?.set("x", 120);
// Another client can edit `shape-2` without replacing the collection.
```

### Lists [#lists]

[`LiveList`](/docs/api-reference/liveblocks-client#LiveList) preserves
concurrent insertions and maintains a shared order. Use it when the order itself
is collaborative, such as layers or columns.

### Text [#text]

[`LiveText`](/docs/api-reference/liveblocks-client#LiveText) resolves edits at
the text-operation level. Concurrent insertions, deletions, and formatting
changes converge without replacing the whole string.

## Design documents for collaboration [#design-documents]

- Use a `LiveMap` keyed by entity ID instead of one large array when entities
  are edited independently.
- Use nested `LiveObject` properties instead of replacing a whole record.
- Keep large binary data outside the document and reference it with
  [`LiveFile`](/docs/products/sync/data-types#livefile).
- Use `LiveText` rather than a plain string when people edit the same text.
- Keep cursors, selections, and other connection state in
  [presence](/docs/products/sync/presence).

## Reconnection [#reconnection]

When a connection is interrupted, Sync reconnects and brings the client up to
date with the room. Use
[`useLostConnectionListener`](/docs/api-reference/liveblocks-react#useLostConnectionListener)
to explain a lost connection and
[`useSyncStatus`](/docs/api-reference/liveblocks-react#useSyncStatus) before
showing that changes are saved.

```tsx
import { useSyncStatus } from "@liveblocks/react/suspense";

function SaveStatus() {
  const status = useSyncStatus({ smooth: true });

  return status === "synchronized" ? "Saved" : "Saving…";
}
```
