Storage is the persistent document inside Sync. Multiple humans and agents can
edit it at the same time, and conflict resolution merges simultaneous changes
without losing unrelated edits. Documents remain after every user disconnects,
unlike [presence](/docs/products/sync/presence), which is temporary.

Documents are built from conflict-free data types, each resolving simultaneous
edits differently. Learn more about each type under
[data types](#data-types).

| Data type                                                             | Description                                                                                                      |
| --------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| [`LiveObject`](/docs/api-reference/liveblocks-client#LiveObject)       | A record of named values, like a JavaScript object. Ideal for structured items such as a shape or a person.       |
| [`LiveList`](/docs/api-reference/liveblocks-client#LiveList)           | An ordered collection. Concurrent inserts, deletes, and moves merge so every client sees the same sequence.       |
| [`LiveMap`](/docs/api-reference/liveblocks-client#LiveMap)             | A key-value collection with dynamic keys. Ideal for items keyed by ID, such as shapes on a canvas.                 |
| [`LiveText`](/docs/api-reference/liveblocks-client#LiveText)           | Collaborative rich text. Simultaneous keystrokes and formatting merge character by character.                      |
| [`LiveFile`](/docs/api-reference/liveblocks-client#LiveFile)           | An immutable reference to an uploaded file, such as an image or video, stored outside the document tree.          |

## Setting up Storage [#setting-up-storage]

Before reading or updating Storage, decide on the shape of your document, and
set the `Storage` type in your config file. This makes every hook and mutation
fully typed. In this example, this canvas document holds a list of shapes.

```tsx file="liveblocks.config.ts"
import { LiveList, LiveObject } from "@liveblocks/client";

// +++
type Shape = LiveObject<{
  x: number;
  y: number;
  color: string;
}>;
// +++

declare global {
  interface Liveblocks {
    // +++
    Storage: {
      shapes: LiveList<Shape>;
    };
    // +++
  }
}
```

Next, create an initial document with
[`initialStorage`](/docs/api-reference/liveblocks-react#setting-initial-storage)
on [`RoomProvider`](/docs/api-reference/liveblocks-react#RoomProvider). It’s
applied once, the first time a room is entered—after that, the stored document
is the source of truth.

```tsx
import { LiveList, LiveObject } from "@liveblocks/client";
import { RoomProvider } from "@liveblocks/react/suspense";

function App({ children }: { children: React.ReactNode }) {
  return (
    <RoomProvider
      id="my-room"
      // +++
      initialStorage={{
        shapes: new LiveList([new LiveObject({ x: 50, y: 100, color: "red" })]),
      }}
      // +++
    >
      {children}
    </RoomProvider>
  );
}
```

## Reading Storage [#reading-storage]

[`useStorage`](/docs/api-reference/liveblocks-react#useStorage) reads a part of
the document, returning it as an immutable value. The selected part updates in
realtime as any user or agent edits it, and the component only re-renders when
that part changes.

```tsx
import { useStorage } from "@liveblocks/react/suspense";

function Canvas() {
  // +++
  const shapes = useStorage((root) => root.shapes);
  // +++

  return (
    <>
      {shapes.map((shape, index) => (
        <Shape key={index} x={shape.x} y={shape.y} color={shape.color} />
      ))}
    </>
  );
}
```

## Updating Storage [#updating-storage]

[`useMutation`](/docs/api-reference/liveblocks-react#useMutation) creates a
callback that modifies the document. Changes apply instantly for the current
user, sync to everyone else in realtime, and merge with any simultaneous edits.

```tsx
import { useMutation } from "@liveblocks/react/suspense";
import { LiveObject } from "@liveblocks/client";

function Toolbar() {
  // +++
  const addShape = useMutation(({ storage }) => {
    storage.get("shapes").push(
      new LiveObject({
        x: 50,
        y: 100,
        color: "red",
      })
    );
  }, []);
  // +++

  return <button onClick={() => addShape()}>Add shape</button>;
}
```

Mutations accept extra arguments after the context object, so you can pass in
values when calling them.

```tsx
import { useMutation } from "@liveblocks/react/suspense";

function ColorPicker({ index }: { index: number }) {
  const setColor = useMutation(
    // +++
    ({ storage }, color: string) => {
      storage.get("shapes").get(index)?.set("color", color);
    },
    // +++
    [index]
  );

  return <input type="color" onChange={(e) => setColor(e.target.value)} />;
}
```

Storage can also be modified from your back end and by AI agents—read
[server-side editing](/docs/products/sync/server-side-editing) and
[agentic editing](/docs/products/sync/agentic-editing).

## Data types [#data-types]

Build the document tree from conflict-free data types. Use plain JSON values for
atomic fields, and a Live structure when nested fields should be edited
independently.

- [`LiveObject`](#liveobject): A record of named values
- [`LiveList`](#livelist): An ordered collection
- [`LiveMap`](#livemap): A key-value collection with dynamic keys
- [`LiveText`](#livetext): Collaborative rich text
- [`LiveFile`](#livefile): A reference to a file stored outside the document
  tree

Each type resolves conflicts differently, described below, and all of them
persist after every client has left the room.

### LiveObject [#liveobject]

[`LiveObject`](/docs/api-reference/liveblocks-client#LiveObject) stores a record
with fixed key names, similar to a JavaScript object. Use it for a person, a
shape, or any other structured item.

```ts
import { LiveObject } from "@liveblocks/client";

const shape = new LiveObject({
  x: 50,
  y: 100,
  color: "red",
});

shape.set("color", "blue");
```

If two clients set the same property at the same time, the last change received
by Liveblocks wins. Unrelated properties are never overwritten—one user can move
a shape while another recolors it, and both edits survive.

### LiveList [#livelist]

[`LiveList`](/docs/api-reference/liveblocks-client#LiveList) is an ordered
collection. Concurrent inserts, deletes, and moves are merged so every client
sees the same sequence.

```ts
import { LiveList, LiveObject } from "@liveblocks/client";

const shapes = new LiveList([new LiveObject({ x: 50, y: 100, color: "red" })]);

shapes.push(new LiveObject({ x: 80, y: 40, color: "blue" }));
```

### LiveMap [#livemap]

[`LiveMap`](/docs/api-reference/liveblocks-client#LiveMap) is a key-value
collection with dynamic keys, ideal for items keyed by ID, such as shapes on a
canvas. If two clients update the same key at the same time, the last change
received by Liveblocks wins.

```ts
import { LiveMap, LiveObject } from "@liveblocks/client";

const shapes = new LiveMap([
  ["shape-1", new LiveObject({ x: 50, y: 100, color: "red" })],
]);

shapes.set("shape-2", new LiveObject({ x: 80, y: 40, color: "blue" }));
```

### LiveText [#livetext]

[`LiveText`](/docs/api-reference/liveblocks-client#LiveText) is a collaborative
rich-text document. Concurrent insertions, deletions, and formatting merge
automatically, character by character, so multiple people can type in the same
text without overwriting each other. Editor packages such as
[`@liveblocks/react-tiptap`](/docs/api-reference/liveblocks-react-tiptap),
[`@liveblocks/react-lexical`](/docs/api-reference/liveblocks-react-lexical), and
[`@liveblocks/react-blocknote`](/docs/api-reference/liveblocks-react-blocknote)
adapt it to those editors. Learn more under
[text editing](/docs/products/sync/text-editing).

```ts
import { LiveText } from "@liveblocks/client";

const caption = new LiveText("Untitled");
```

### LiveFile [#livefile]

[`LiveFile`](/docs/api-reference/liveblocks-client#LiveFile) is an immutable
reference to a file uploaded to Liveblocks. Use it for images, videos, and other
binaries that should not live in the JSON tree. Upload with
[`useUploadFile`](/docs/api-reference/liveblocks-react#useUploadFile), then
store the returned `LiveFile` in Storage.

```tsx
import { useMutation, useUploadFile } from "@liveblocks/react/suspense";

function UploadAttachment() {
  // +++
  const uploadFile = useUploadFile();
  // +++

  const addAttachment = useMutation(({ storage }, liveFile) => {
    storage.get("attachments").push(liveFile);
  }, []);

  return (
    <input
      type="file"
      onChange={async (event) => {
        const file = event.currentTarget.files?.[0];
        if (!file) return;
        // +++
        addAttachment(await uploadFile(file));
        // +++
      }}
    />
  );
}
```

See [file size limits](/docs/pricing/limits) for upload constraints.

## Nested data [#nested-data]

`LiveObject`, `LiveList`, and `LiveMap` can contain other Live structures, so
you can model a full document tree, with each branch edited independently.
`LiveFile` is a leaf and cannot contain children.

```ts file="liveblocks.config.ts"
import { LiveList, LiveMap, LiveObject } from "@liveblocks/client";

type Person = LiveObject<{
  name: string;
  pets: LiveList<string>;
}>;

declare global {
  interface Liveblocks {
    Storage: {
      people: LiveMap<string, Person>;
    };
  }
}
```

The
[nesting data types tutorial](/docs/tutorial/react/getting-started/nesting-data-types)
walks through a nested document in the editor.

## Multiplayer undo/redo [#multiplayer-undo-redo]

When using Storage, each user has an independent undo stack which is saved in
memory until the users leaves the page. Using undo will reverts the user’s
Storage changes without reversing work made by other collaborators.

### Creating undo/redo buttons

The [`useUndo`](/docs/api-reference/liveblocks-react#useUndo) and
[`useRedo`](/docs/api-reference/liveblocks-react#useRedo) hooks can be used to
trigger undo/redo actions. Additionally
[`useCanUndo`](/docs/api-reference/liveblocks-react#useCanUndo) and
[`useCanRedo`](/docs/api-reference/liveblocks-react#useCanRedo) can be used to
check if there are any actions to undo/redo, helpful for disabling buttons.

```tsx
import {
  useCanRedo,
  useCanUndo,
  useRedo,
  useUndo,
} from "@liveblocks/react/suspense";

function HistoryButtons() {
  // +++
  const undo = useUndo();
  const redo = useRedo();
  const canUndo = useCanUndo();
  const canRedo = useCanRedo();
  // +++

  return (
    <>
      // +++
      <button onClick={undo} disabled={!canUndo}>
        Undo
      </button>
      <button onClick={redo} disabled={!canRedo}>
        Redo
      </button>
      // +++
    </>
  );
}
```

### Pause and resume history [#pause-resume]

Pause history when a single gesture should count as one undo step, such as
dragging a shape. Intermediate positions still sync to other clients, but undo
restores the position from before the drag.

```tsx
import { useHistory } from "@liveblocks/react/suspense";

function Canvas() {
  // +++
  const { pause, resume } = useHistory();
  // +++

  return <Shape onDragStart={() => pause()} onDragEnd={() => resume()} />;
}
```

[`useHistory`](/docs/api-reference/liveblocks-react#useHistory) also exposes
`disable` for when a local change should not enter the stack at all. See
[`Room.history`](/docs/api-reference/liveblocks-client#Room.history) for the
client API.

### Presence history [#presence-history]

Undo only affects Storage by default. If a presence value should move with the
document, such as the currently selected shape, pass `{ addToHistory: true }`
when updating presence.

```tsx
import { useUpdateMyPresence } from "@liveblocks/react/suspense";

function SelectShape({ shapeId }: { shapeId: string }) {
  const updateMyPresence = useUpdateMyPresence();

  return (
    <button
      onClick={
        () =>
          // +++
          updateMyPresence({ selectedShapeId: shapeId }, { addToHistory: true })
        // +++
      }
    >
      Select
    </button>
  );
}
```

This also works with `setMyPresence` inside a mutation. For framework-specific
walkthroughs, read the
[React](/docs/guides/how-to-use-liveblocks-multiplayer-undo-redo-with-react),
[Zustand](/docs/guides/how-to-use-liveblocks-multiplayer-undo-redo-with-zustand),
and [Redux](/docs/guides/how-to-use-liveblocks-multiplayer-undo-redo-with-redux)
undo/redo guides.
