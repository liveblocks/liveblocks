Feeds is part of Sync. Use it for ordered, persistent message streams inside a
room: chat messages, agent output, activity logs, and workflow progress. Feed
updates appear in realtime for connected clients and remain available when they
reconnect.

<Banner title="Get started with Feeds" type="info">

Build a working Next.js app with the
[Feeds get-started guide](/docs/get-started/nextjs-feeds).

</Banner>

## What to build with Feeds [#what-to-build]

- Human and AI chat interfaces
- Agent output and intermediate progress
- Activity streams and audit-style timelines
- Multi-agent orchestration and background workflow status
- Structured messages between servers and connected clients

## What Feeds provides [#features]

- **Realtime updates**: New feeds and messages appear without polling.
- **Persistent messages**: Clients can reconnect and load earlier messages.
- **Structured data**: Define the JSON message shape that fits each workflow.
- **Pagination**: Load long feed lists and message histories incrementally.
- **Metadata filtering**: Find feeds by application-specific metadata.
- **Client and server APIs**: Create and read feeds from React, JavaScript,
  Node.js, REST, or workflow integrations.
- **Room permissions**: Give users read-only or write access to feeds.

## Build a chat interface [#chat-interfaces]

A chat interface is one feed whose messages contain the information needed to
render each turn. Your application defines the message schema and UI; Feeds
handles persistence, realtime updates, pagination, and client/server access.

```tsx title="Chat.tsx"
import {
  useCreateFeedMessage,
  useFeedMessages,
} from "@liveblocks/react/suspense";

export function Chat({ feedId }: { feedId: string }) {
  const { messages } = useFeedMessages(feedId);
  const createMessage = useCreateFeedMessage();

  return (
    <div>
      {messages.map((message) => (
        <article key={message.id} data-role={message.data.role}>
          {message.data.content}
        </article>
      ))}
      <button
        onClick={() =>
          createMessage(feedId, {
            role: "user",
            content: "What changed?",
          })
        }
      >
        Send
      </button>
    </div>
  );
}
```

Start a server-side assistant or agent workflow after the user sends a message,
then append its result with
[`Liveblocks.createFeedMessage`](/docs/api-reference/liveblocks-node#post-rooms-roomId-feeds-feedId-messages).
Connected clients receive the new message automatically.

## List and filter feeds [#listing-feeds]

Use [`useFeeds`](/docs/api-reference/liveblocks-react#useFeeds) to render feeds
in the current room. Results update in realtime when feeds are created, updated,
or deleted.

```tsx title="FeedList.tsx"
import { useFeeds } from "@liveblocks/react/suspense";

export function FeedList() {
  const { feeds } = useFeeds({
    metadata: { kind: "chat" },
    limit: 20,
  });

  return (
    <nav>
      {feeds.map((feed) => (
        <a key={feed.feedId} href={`/chat/${feed.feedId}`}>
          {feed.metadata.title ?? feed.feedId}
        </a>
      ))}
    </nav>
  );
}
```

Pass `metadata` to return feeds whose metadata contains every provided key/value
pair. Store fields you will query directly in feed metadata, and keep larger or
frequently changing data elsewhere.

## Paginate feeds and messages [#pagination]

`useFeeds` and `useFeedMessages` load up to 50 items by default. Both hooks
return pagination controls, so interfaces can load earlier data without
replacing items already rendered.

```tsx title="PaginatedMessages.tsx"
const { messages, fetchMore, hasFetchedAll, isFetchingMore, fetchMoreError } =
  useFeedMessages(feedId, { limit: 20 });

// Render messages, then load an earlier page when needed.
if (!hasFetchedAll) {
  return (
    <button disabled={isFetchingMore} onClick={fetchMore}>
      {isFetchingMore ? "Loading…" : "Load earlier messages"}
    </button>
  );
}
```

Use `fetchMore` to request the next page, `hasFetchedAll` after the final page,
and `fetchMoreError` to render errors from later pages separately from the
initial load. Use the same pattern with `useFeeds` for a room’s feed list.

## Integrate server and agent workflows [#integrating-workflows]

Create and update feeds from your server when work starts outside the browser.
This works with custom workers, AI SDKs, orchestration frameworks, and
automation tools such as n8n.

```ts title="run-workflow.ts"
await liveblocks.createFeed({
  roomId: "my-room",
  feedId: "workflow-42",
  metadata: { kind: "workflow", title: "Generate launch plan" },
});

await liveblocks.createFeedMessage({
  roomId: "my-room",
  feedId: "workflow-42",
  data: { type: "status", status: "running" },
});
```

Use deterministic feed and message IDs if a trigger can be delivered more than
once. Use Feeds for durable output, [Presence](/docs/products/sync/presence) for
temporary activity such as “searching” or “editing”, and
[Agentic editing](/docs/products/sync/agentic-editing) when the workflow edits
the shared document itself.

The [Liveblocks n8n integration](/docs/integrations/n8n-nodes) exposes
Liveblocks API operations as workflow nodes. Other systems can use the
[Node.js API](/docs/api-reference/liveblocks-node#Feeds) or
[REST API](/docs/api-reference/rest-api-endpoints#Feeds) directly.

## Authentication and permissions [#authentication-and-permissions]

Feeds uses the same room authentication flow as the rest of Sync. Configure user
identity with [Authentication](/docs/authentication), then choose a room scope
for each user:

| Scope         | Access                                                |
| ------------- | ----------------------------------------------------- |
| `feeds:read`  | Read feeds and feed messages                          |
| `feeds:write` | Read and create, update, or delete feeds and messages |
| `feeds:none`  | No access to Feeds                                    |

Use `feeds:read` for viewers and `feeds:write` for users who can send messages
or manage feeds. Server-side calls with a secret key are not limited by an end
user’s access token, so validate application permissions before acting on their
behalf.
