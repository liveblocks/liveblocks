Choose PowerSync when users need a local SQLite dataset and offline writes that
upload to your application back end. Choose Liveblocks when the feature centers
on concurrent editing of a document, canvas, or workflow.
[PowerSync architecture](https://docs.powersync.com/architecture/architecture-overview)
· [Liveblocks Sync](/docs/products/sync)

A field technician's offline job list and a design team's shared canvas have
different requirements. The first needs local records and an upload path. The
second needs a shared editing model and participant experience.

## Compare the data and write paths [#compare-the-data-and-write-paths]

| Area | Liveblocks Sync | PowerSync |
| --- | --- | --- |
| Client data model | Shared documents with live structures | Local SQLite tables and queries |
| Data reaching the client | Synchronized document state | Selected source-database records |
| Writes | Supported client and server editing APIs | Local SQLite changes queued for upload through your back end |
| Conflict behavior | Defined by the chosen shared-data type and operation | Your back end applies write validation and conflict-handling rules |
| Text editing | Supported `LiveText` or Yjs editor integrations | Add an editing model; PowerSync links to a Yjs demo |
| Self-hosting | Paid Enterprise Sync add-on | Self-hosted service configurations |
| Main implementation work | Model the document and connect application permissions | Define the local dataset, upload API, and back-end write rules |

## How does offline SQLite differ from an open collaborative document? [#how-does-offline-sqlite-differ-from-an-open-collaborative-document]

PowerSync keeps a local SQLite database and a durable queue of changes to upload.
Liveblocks Storage synchronizes a loaded document and queues unconfirmed changes
for reconnect. A durable offline database and edits buffered within an open
session are different guarantees.
[PowerSync client architecture](https://docs.powersync.com/architecture/client-architecture)
· [Liveblocks synchronization](/docs/products/sync/storage)

| Requirement | PowerSync | Liveblocks Storage |
| --- | --- | --- |
| Query assigned jobs while offline | Query the synchronized local SQLite dataset | Read the already-loaded document |
| Queue database writes for a later upload | Persistent upload queue; application back end validates changes | Queue document edits within the active client session |
| Reopen after the app has closed | Local database and queue persistence are part of the client design | Reconnect support covers the loaded session; persistence across restarts requires a separate design |
| Merge edits inside a paragraph | Add an editing model, such as the published Yjs example | Use a supported text integration |

Choose PowerSync when the offline relational dataset is the core requirement.
Choose Liveblocks when the core surface is a shared document with an editing and
review experience. A product may have both.

## Example: an offline job list [#example-an-offline-job-list]

PowerSync clients read from local SQLite. Writes update the local database and
enter an upload queue. Your upload implementation sends those changes to the
application back end, where you apply business rules and authorization. Failed
uploads can be retried when connectivity returns.
[PowerSync client architecture](https://docs.powersync.com/architecture/client-architecture)

Consider a field-service app where a technician needs an assigned set of jobs,
equipment records, and forms while disconnected. Evaluate the local dataset,
queries, upload behavior, and rejected changes across the full visit. Those
requirements make PowerSync's database-centered model relevant.

For a design tool where people work on the same canvas, evaluate the shared
editing operations and participant experience. Liveblocks may fit that surface
without making a local relational database the application's primary client model.

## Can PowerSync support collaborative text editing? [#can-powersync-support-collaborative-text-editing]

Yes, by combining database synchronization with an editing model. PowerSync
lets the application back end determine how uploaded changes are applied. Its
documentation describes conflict-handling choices, including custom strategies.
Your write API applies the business rules when queued changes reach the server.
[PowerSync update conflicts](https://docs.powersync.com/usage/lifecycle-maintenance/handling-update-conflicts)

For collaborative text, PowerSync's guide links to a Yjs demo. Compare that
complete architecture with a Liveblocks editor integration, including document
storage, uploads, and the behavior of concurrent edits.
[PowerSync text editing guide](https://docs.powersync.com/integration-guides/yjs)

## Pricing and deployment [#pricing-and-deployment]

For PowerSync, include its service, storage, source database, and write API. For
Liveblocks, include Sync and the application services around the documents.
Budget additional editing or review components explicitly.
