Choose Liveblocks when users need to edit a shared document, canvas, or workflow.
Choose Supabase when the core requirement is a Postgres back end with realtime
database updates. Use both when business records belong in Postgres and the
product also needs a dedicated editing layer. [Liveblocks Sync](/docs/products/sync)
· [Supabase database](https://supabase.com/docs/guides/database)

Liveblocks supplies the shared-data structures and editing integrations.
Supabase supplies the relational application database. Use Liveblocks for the
content people edit together and Supabase for the records your application
queries.

## Compare the responsibilities [#compare-the-responsibilities]

| Area | Liveblocks | Supabase |
| --- | --- | --- |
| Persistent data | Shared documents through [Storage](/docs/products/sync/storage) in [Sync](/docs/products/sync) | Postgres tables and relationships |
| Realtime updates | Document synchronization, presence, and events | Broadcast, Presence, and Postgres Changes |
| Shared text | [LiveText](/docs/products/sync/storage#LiveText) and supported Yjs integrations | Add the editor synchronization model your app needs |
| Collaboration interface | Products for [Comments](/docs/products/comments) and [Notifications](/docs/products/notifications) alongside Sync | Realtime UI components include cursors, presence, and chat |
| Main architecture question | Which product surfaces should share a document? | Which data and business rules should live in Postgres? |

## Does Supabase Realtime merge concurrent text edits? [#does-supabase-realtime-merge-concurrent-text-edits]

[Supabase Realtime](https://supabase.com/docs/guides/realtime) delivers
broadcasts, presence, and database changes. A collaborative text editor also
needs rules for combining edits inside the text. Add an editor synchronization
model, such as [Yjs](https://docs.yjs.dev/), or use a supported Liveblocks
editor integration. A database subscription delivers the changed value; the
editor model determines how concurrent text edits merge.
[Supabase Realtime](https://supabase.com/docs/guides/realtime) ·
[Liveblocks text editing](/docs/products/sync/text-editing)

## Choose around the interaction [#choose-around-the-interaction]

For an order dashboard, a row update may be enough: the server changes an
order's status, and connected clients display the new value. Supabase is a
natural option when Postgres is already the application's source of truth.

For a planning board, store each card in a live structure. One person changes
its title while another changes its due date: because those are separate keys,
both edits can remain. The UI reflects a shared result without an
application-specific event protocol for merging those fields.
[Conflict resolution](/docs/guides/how-conflict-resolution-works-in-liveblocks-sync)

[Sync](/docs/products/sync)'s behavior depends on the data type. Separate fields
can preserve separate changes; concurrent writes to the same scalar field
resolve by server arrival order. A shared-data system doesn't remove the need to
model your document deliberately.
[Conflict resolution](/docs/guides/how-conflict-resolution-works-in-liveblocks-sync)

## Can I use Liveblocks with Supabase? [#can-i-use-liveblocks-with-supabase]

Yes. Keep business records in Supabase and editable documents in Liveblocks. The
documented integration sends a reporting copy from Liveblocks to Supabase
through webhooks. It is one-way and eventually consistent; updating that copy in
Postgres does not edit the Liveblocks document.
[Supabase integration](/docs/integrations/supabase)

For a planning app, this division gives each kind of data a clear owner:

| Data | Authoritative system | How the app uses it |
| --- | --- | --- |
| Projects, accounts, and billing | Supabase | Query records and enforce application rules |
| Shared board and card content | Liveblocks | Participants edit the same document |
| Searchable board summary | Supabase mirror | Query a derived copy; tolerate webhook delay |

In this design, store the Liveblocks room ID with the project record so your
server can authorize the correct document. Keep mirrored content read-only from
the application's perspective.

## How do the costs differ? [#how-do-the-costs-differ]

Supabase Pro starts at $25 per month and includes $10 in compute credits, enough
for one Micro instance. Additional projects and usage can increase that amount.
Liveblocks is an additional service when the application keeps Supabase.
[Supabase pricing](https://supabase.com/pricing)

For an illustrative monthly workflow with 1,000 active editing sessions, two
participants per session, and 15 minutes of continuous collaboration, the
Liveblocks collaboration meter is 30,000 minutes. At $0.002 per minute, that is
$60 of metered usage before credits. It excludes stored data, updates, comments,
and other usage. Solo sessions are not billed as collaboration minutes.
[Collaboration-minute definition](/docs/pricing/faqs#What-counts-as-a-realtime-collaboration-minute)

That calculation measures the editing layer, not a replacement for the Supabase
bill. Apply the selected plan's credits once across all Liveblocks usage.
[Plans and credits](/docs/pricing/plans)

Supabase supports self-hosting. Liveblocks offers self-hosted Sync as a paid
Enterprise add-on. Your infrastructure, database, backups, and operations remain
part of a self-hosted budget.
[Supabase deployment](https://supabase.com/docs/guides/self-hosting) ·
[Liveblocks deployment](/docs/platform/data-storage#Self-hosting)
